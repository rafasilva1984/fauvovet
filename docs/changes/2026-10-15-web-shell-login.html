Web: login, cadastro, seleção de clínica, shell responsivo e aparência por tenant

ID: 2026-10-15-web-shell-login · Data: 15/10/2026 · Versão: 0.1.0 · Módulo: A. Administração SaaS e tenants · §7 UX/UI · §4.1 Branding · Estado: implementado e testado localmente

1. Objetivo e contexto

Entregar o fluxo de referência 1 do CLAUDE.md §7.3 — entrar → selecionar clínica/unidade → painel contextual — com interface real, responsiva e acessível sobre a API do incremento anterior, mais cadastro de nova clínica, unidades, equipe (leitura) e personalização visual por tenant.

Critério de aceite: jornadas funcionam em desktop e em celular (Pixel 7), um tenant não vê dados de outro na interface, a navegação reflete o papel (e a API nega o resto), as telas passam o axe WCAG 2.2 AA em claro e escuro, e pnpm verify --e2e passa.

2. O que mudou

Antes: apenas API. Depois: novo pacote apps/web (Next.js 16.4, React 19.3, Tailwind CSS 4.3).

Rota (sob /fauvovet)Conteúdo

  • Design system: app/globals.css (tokens --fv-*, tema claro/escuro), components/ui.tsx, components/icons.tsx (ícones e marca próprios), components/app-shell.tsx (sidebar no desktop; topo + barra inferior + folha de conta no celular), components/auth-frame.tsx.
  • Sessão: lib/session.tsx e lib/api.ts (cookie HttpOnly + X-CSRF-Token); lib/theme.ts aplica o tema do tenant.
  • Configuração: next.config.ts — basePath de BASE_PATH, output: standalone, distDir via NEXT_DIST_DIR, CSP e cabeçalhos de segurança, rewrite /api/* → API_INTERNAL_URL.
  • Scripts: scripts/web-run.mjs (Next com .env da raiz e NODE_ENV correto), scripts/e2e-api.mjs (API de E2E com banco _test recriado) e apps/web/e2e/servers.ts (sobe/derruba API e web de E2E); pnpm dev agora sobe também a web.
  • Testes: apps/web/lib/api.test.ts (4 unitários) e apps/web/e2e/*.spec.ts (11 cenários × 2 projetos = 22).
  • Correções encontradas pelos testes: asterisco de campo obrigatório entrava no nome acessível; aria-labelledby da seção “Nova unidade” apontava para si mesma; next build falhava ao herdar NODE_ENV=development do .env.
  • Dependências novas: next 16.4.0, react/react-dom 19.3.1, tailwindcss + @tailwindcss/postcss 4.3.3, postcss, @playwright/test 1.64.1, @axe-core/playwright (dev). Nenhuma alteração de banco/migração.

3. Pré-requisitos (WSL2 e Git Bash)

  • Os mesmos do incremento anterior (Node 24, pnpm 12.4.2, PostgreSQL local via pnpm db:start).
  • Portas: 3000 (web dev), 4000 (API dev); E2E usa 127.0.0.1:3100/127.0.0.1:4100 e o banco fauvovet_test.
  • Navegador de teste (uma vez, ~120 MB, sem sudo no WSL verificado): pnpm --filter @fauvovet/web exec playwright install chromium.
  • Variáveis novas usadas (já em .env.example): WEB_PORT, API_INTERNAL_URL. Opcionais: E2E_WEB_PORT, E2E_API_PORT, E2E_PASSWORD, NEXT_DIST_DIR.

Git Bash: NOT RUN. Em distros Linux mínimas o Chromium pode exigir bibliotecas do sistema (playwright install-deps precisa de sudo); no WSL Ubuntu 26.04 desta verificação não foi necessário.

4. Passo a passo para aplicar a mudança

Instalação existente (vinda do incremento anterior)

git pull --ff-only
pnpm install --frozen-lockfile
pnpm --filter @fauvovet/web exec playwright install chromium   # só para E2E
pnpm dev

Resultado esperado: Web: http://localhost:3000/fauvovet · API: http://127.0.0.1:4000/fauvovet/api/v1/health. Abra http://localhost:3000/fauvovet → redireciona para /login.

Instalação nova

git clone https://github.com/rafasilva1984/fauvovet.git && cd fauvovet
pnpm bootstrap
pnpm dev

Build de produção da web

BASE_PATH=/fauvovet API_INTERNAL_URL=http://127.0.0.1:4000 pnpm --filter @fauvovet/web build
pnpm --filter @fauvovet/web start   # serve em WEB_PORT

BASE_PATH e API_INTERNAL_URL são fixados no build; mude-os e refaça o build para outro destino.

5. Como testar

Automático

pnpm db:start
pnpm verify --e2e      # gate completo incluindo E2E
pnpm test:e2e          # apenas E2E (constrói web em .next-e2e e sobe API/web próprias)

Manual (senha dos usuários fictícios = SEED_PASSWORD do .env)

  1. ana.titular@aurora.exemplo.test → tela de contexto (2 unidades) → escolha “Aurora — Centro” → painel “Gestão da clínica”, contagens, atalhos e atividade recente.
  2. Unidades → crie “Aurora — Norte”, cidade fictícia, UF mg → aparece na lista com UF “MG”; repetir o nome → mensagem de conflito.
  3. Aparência → digite #808080 na primária → aviso “abaixo do mínimo” e botão desabilitado; #1d4e89 → salvar → recarregar mantém a cor. “Restaurar padrão FauvoVet” e salvar.
  4. bruno.vet@… → menu mostra só Painel e Unidades; acessar /fauvovet/equipe direto mostra aviso de permissão (API responde 403).
  5. diana.titular@horizonte.exemplo.test → entra direto (1 unidade) → Unidades mostra só “Atendimento domiciliar”, nada de “Aurora”.
  6. eva.plantonista@exemplo.test → escolha Aurora → “Trocar clínica/unidade” → Vet Horizonte → dados mudam por completo.
  7. No celular (ou DevTools, 412×915): barra inferior, menu da conta no ícone ☰, “Sair” → volta ao login; voltar para /painel redireciona ao login.
  8. /fauvovet/cadastro → “Profissional autônomo (CPF)”, CPF 529.982.247-25 (fictício válido), senha curta → erro; senha com 12+ → entra no painel do novo ambiente.

Falhas que devem ser rejeitadas

  • Senha incorreta → “E-mail ou senha incorretos.” (mesma mensagem para e-mail inexistente).
  • Rotas autenticadas sem sessão → redirecionam ao login; a API retorna 401.
  • Itens ocultos na UI continuam negados pela API (testado no incremento anterior em rbac.test.ts).

7. Publicação na Locaweb / FileZilla (se aplicável)

Não publicável ainda. Plano Locaweb não verificado. A web pode ser servida como Node (output: standalone) atrás de proxy reverso; não é um site estático para FTP, pois depende da API e do PostgreSQL. Quando houver VPS: build com BASE_PATH=/fauvovet, nginx roteando /fauvovet/api/ à API e /fauvovet à web, COOKIE_SECURE=true, PUBLIC_ORIGIN com o domínio HTTPS. Nada deve ser enviado por FileZilla neste momento.

8. Backup e rollback

  • Sem migrações nem mudanças de dados neste incremento: rollback = git revert <commit> deste incremento (a API continua funcionando sozinha).
  • Artefatos locais gerados (apps/web/.next, .next-e2e, test-results, playwright-report, .perf) são ignorados pelo Git e recriáveis.
  • O E2E recria o schema do banco fauvovet_test; o banco fauvovet_dev não é tocado.

9. Troubleshooting

SintomaCausa / ação
Cannot read properties of null (reading 'useContext') no next buildBuild com NODE_ENV=development. Use pnpm --filter @fauvovet/web build (o script força production).
E2E: …:4100 … is already usedProcesso de uma execução interrompida ficou vivo. ss -ltnp | grep 4100 e encerre o PID.
E2E demora minutos para começar (WSL2)Com networkingMode=mirrored, conectar em porta fechada de 127.0.0.1 não é recusado e fica pendurado. Por isso e2e/servers.ts sobe os servidores com sondagens de 1 s em vez do webServer do Playwright (de 5 min 18 s para ~33 s).
E2E: Executable doesn't existRode pnpm --filter @fauvovet/web exec playwright install chromium.
Login funciona mas toda mutação dá 403 csrf_failedPUBLIC_ORIGIN diferente da URL aberta no navegador (ex.: 127.0.0.1 vs localhost).
Console do navegador mostra 401 em /auth/me na tela de loginEsperado: verificação de sessão sem cookie (aparece 2× no dev por StrictMode).
Web em outro caminho/servidor chama API erradaBASE_PATH/API_INTERNAL_URL são de build; refaça o build.

Limitações: sem recuperação de senha, convite, edição de membros, logo/favicon do tenant; CSP com 'unsafe-inline' em scripts (ADR-009); pnpm dev encerrado por SIGTERM pode deixar tsc --watch órfão (Ctrl+C funciona).
