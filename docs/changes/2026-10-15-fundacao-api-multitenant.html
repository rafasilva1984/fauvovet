Fundação: monorepo, PostgreSQL com RLS e API multi-tenant

ID: 2026-10-15-fundacao-api-multitenant · Data: 15/10/2026 · Versão: 0.1.0 · Módulo: A. Administração SaaS e tenants · Estado: implementado e testado localmente (API); web pendente

1. Objetivo e contexto

Criar a base executável do FauvoVet com isolamento rígido entre clínicas desde o primeiro commit: autenticação segura, seleção explícita de clínica/unidade, permissões negadas por padrão no backend e Row-Level Security no PostgreSQL, comprovados com dois tenants fictícios.

Critério de aceite: API e banco sobem localmente com um comando; um usuário do tenant A não consegue ler, listar, criar ou alterar dados do tenant B por API (IDs previsíveis, tenant_id manipulado) nem por SQL direto com o papel da aplicação; pnpm verify passa.

3. Pré-requisitos (WSL2 e Git Bash)

  • Node.js 24.x (verificado: v24.21.0) e pnpm 12.4.2 — via mise install ou corepack enable.
  • Git 2.4x+ (verificado: 2.53.0).
  • Não é necessário Docker nem sudo: o PostgreSQL 18 local vem como binário npm e roda em .data/pg, porta 54329, apenas em 127.0.0.1.
  • Portas livres: 54329 (PostgreSQL), 4000 (API).
  • Variáveis: todas em .env.example, com valores fictícios de desenvolvimento (prefixo dev-only-). O bootstrap copia para .env sem sobrescrever.

Git Bash (Windows): os scripts usam apenas Node e resolvem o binário @embedded-postgres/windows-x64, mas este fluxo ainda não foi executado no Git Bash (NOT RUN). Se falhar, use o WSL2 e registre o erro em docs/TESTING.md.

4. Passo a passo para aplicar a mudança

Instalação nova (WSL2/Linux; Git Bash: mesmos comandos)

git clone https://github.com/rafasilva1984/fauvovet.git
cd fauvovet
mise install            # opcional: instala Node 24 e pnpm 12.4.2 conforme mise.toml
pnpm bootstrap          # .env fictício → pnpm install → contratos → PostgreSQL local (setup) → build API → migrate → seed

Resultado esperado ao final: Seed fictício aplicado: 2 tenants, 3 unidades, 6 usuários. e Ambiente pronto.

Subir a API

pnpm dev
# em outro terminal:
curl -s http://127.0.0.1:4000/fauvovet/api/v1/health
# {"status":"ok","database":"up",...}

Atualizar instalação existente

git pull --ff-only
pnpm install --frozen-lockfile
pnpm --filter @fauvovet/contracts build && pnpm --filter @fauvovet/api build
pnpm db:start && pnpm db:migrate     # migrações já aplicadas são ignoradas (checksum conferido)

Usando PostgreSQL próprio (Docker/nativo)

Crie os papéis fauvovet_migrator (dono dos bancos) e fauvovet_app (NOSUPERUSER NOBYPASSRLS) e os bancos fauvovet_dev/fauvovet_test como em scripts/db-local.mjs › setup, ajuste as URLs no .env e rode pnpm bootstrap --external-db.

5. Como testar

Automático

pnpm db:start
pnpm verify                  # gate completo (resumo PASS/FAIL/NOT RUN no final)
pnpm test:tenant-isolation   # somente a suíte de isolamento (15 testes)

Os testes de integração recriam o schema do banco fauvovet_test a cada execução e recusam qualquer banco que não seja local e terminado em _test.

Manual (dados fictícios; senha = SEED_PASSWORD do .env)

B=http://127.0.0.1:4000/fauvovet/api/v1
# 1. Login como recepção do tenant A (contexto escolhido explicitamente)
curl -s -c /tmp/fv.jar -H 'content-type: application/json' \
  -d '{"email":"carla.recepcao@aurora.exemplo.test","password":"fauvovet-demo-2026"}' $B/auth/login
# → memberships[0].units com 2 unidades, "context": null, "csrfToken": "..."
# 2. Sem contexto, rotas de tenant respondem 409 context_required
curl -s -b /tmp/fv.jar $B/units
# 3. Selecionar contexto (substitua MEMBERSHIP e CSRF pelos valores do passo 1)
curl -s -b /tmp/fv.jar -H 'content-type: application/json' -H "x-csrf-token: CSRF" \
  -d '{"membershipId":"MEMBERSHIP"}' $B/auth/context
# 4. Recepção lista unidades (200) mas não membros (403)
curl -s -b /tmp/fv.jar $B/units ; curl -s -b /tmp/fv.jar $B/members
# 5. Unidade do tenant B por ID previsível → 404
curl -s -b /tmp/fv.jar $B/units/0b000000-0000-4000-8000-0000000000b1

Falhas que DEVEM ser rejeitadas (cobertas por teste)

  • POST sem X-CSRF-Token, com token de outra sessão ou com Origin de outro site → 403.
  • Vínculo de outro usuário ou unidade de outro tenant em /auth/context → 403.
  • tenantId no corpo/query/cabeçalho → ignorado; dado criado no tenant da sessão.
  • SQL com o papel fauvovet_app: sem contexto vê 0 linhas; INSERT/UPDATE para outro tenant bloqueado por RLS; FK composta impede cruzar tenants; DELETE em auditoria negado.
  • Senha errada 3× (configurável) → 429 account_locked; tema com contraste < 4.5:1 → 422.

7. Publicação na Locaweb / FileZilla (se aplicável)

Não publicável neste incremento. O plano Locaweb não foi verificado (docs/DEPLOY_LOCAWEB.md) e a API exige Node.js persistente + PostgreSQL 18 com dois papéis — incompatível com hospedagem só de arquivos. Nada deve ser enviado por FileZilla agora. Quando houver VPS: build (pnpm build), migração com backup prévio, proxy /fauvovet/api/ → API sem reescrita, COOKIE_SECURE=true, TRUST_PROXY=true, segredos apenas no servidor.

8. Backup e rollback

  • Código: git revert <commit> deste incremento (nunca reset --hard/force-push em branch compartilhada).
  • Banco local de desenvolvimento: os dados são fictícios e recriáveis. Para recomeçar: pnpm db:stop, mover a pasta .data/pg para fora do projeto (ex.: .data/pg.bak) e rodar pnpm bootstrap. Mover em vez de apagar preserva a cópia até você confirmar.
  • Migrações: forward-only. A 0001 é a primeira; reverter em ambiente com dados reais exigiria migração corretiva + backup restaurável. Não há produção.
  • O .env existente nunca é sobrescrito pelo bootstrap.
